# Proposal: адресация карточки сервера как `(connection_uuid, node_id)`

## Зачем

Юзеры видят тост «Error when retrieving configuration from API», хотя VPN
уже поднялся с локальным конфигом. Причина: клиент при рефреше зовёт
`/v1/config` со старым `node_id`, бэк отвечает `404 node_not_found`, клиент
падает обратно на кэш. Нужен контракт, при котором пара стабильно
адресует карточку, а 404 означает только «этой пары больше нет в каталоге».

## Модель (как у вас устроено)

На **каждой ноде** создан свой инстанс connection: клиентские настройки
(ключи / UUID / привязка к подписке / протокол) одинаковые по смыслу,
транспорт ноды разный (host, port, server keys, reality, junk).

| Сущность | Поле в API | Что несёт |
|----------|------------|-----------|
| connection | `connection_uuid` / в запросах `connection_id` | Юзер-специфика: клиентские ключи, подписка, протокол |
| node | `node_id` | Нода: IP/host, порт, server_pub_key, reality, AWG junk |
| карточка в приложении | **пара** `(connection_uuid, node_id)` | Join: рабочий конфиг = connection ⊕ node |

`connection_uuid` **может повторяться** у разных нод одной подписки — это OK.
Уникальность строки списка = **пара**, не один uuid.

Выданный конфиг = join(connection, node): одни клиентские ключи, разный
endpoint/транспорт в зависимости от ноды.

## Что сломано сейчас

1. В `/v1/services` → `connections[]` часто **нет `node_id`**, при этом
   `connection_uuid` один на много нод (Suomi / Swe / NL / …).
2. Клиент без `node_id` зовёт `/v1/config` только с `connection_id` →
   бэк отдаёт произвольную ноду → в UI клоны одной машины.
3. Когда `node_id` уже сохранён локально, а ноду сняли/пересоздали →
   `/v1/config` даёт `node_not_found`, хотя локальный пир ещё жив →
   ложный error toast при успешном коннекте.

Связанный баг-репорт: `bug-services-duplicate-connection-uuid.md`.

## Контракт API

### 1. `/v1/services` — обе части ключа в каждом элементе `connections[]`

```json
{
  "connection_label": "Suomi · AmneziaWG",
  "connection_uuid": "1ac65b82-....",
  "node_id": "7f3c9a01-....",
  "country_code": "FI",
  "country_name": "Finland",
  "env": "wl",
  "service_protocol": "awg"
}
```

Требования:

- `node_id` — обязателен, уникален per физическая нода, **стабилен во времени**.
- Смена IP/порта/ключей ноды → **тот же** `node_id`, новый материал в `/v1/config`.
- Новая машина вместо старой → новый `node_id` (клиент увидит новую карточку
  после re-sync и уберёт старую).
- `connection_uuid` может быть общим на группу нод одного logical connection;
  уникальность карточки только в паре с `node_id`.
- Ноду вывели из каталога → её строки **нет** в `/v1/services` (не оставлять
  «зомби», по которым вечный 404).

### 2. `/v1/config` — резолв по паре

Запрос (фрагмент):

```json
{
  "auth_data": { "api_key": "..." },
  "connection_id": "1ac65b82-....",
  "node_id": "7f3c9a01-....",
  "service_protocol": "awg",
  "..."
}
```

Правила резолва:

| Вход | Поведение |
|------|-----------|
| Есть `connection_id` + `node_id`, пара существует | Конфиг = join именно этой пары |
| Пара не найдена / нода не в каталоге | **404** тело с `status: 404`, `message: "node_not_found"` (или аналог). **Не** подставлять другую ноду молча |
| Только `connection_id`, без `node_id` | Legacy: выбор по country+protocol (недетерминированно). Задокументировать; только для старых клиентов |
| `node_id` без валидного connection / auth | 4xx как сейчас (auth / not found) |

Явная ошибка на неизвестной паре нужна клиенту: тихий fallback на локальный
конфиг + re-sync `/v1/services`, без пугающего тоста, когда локальный конфиг
ещё рабочий.

### 3. Edge cases

- **Смена страны в UI** — клиент **не** шлёт старый `node_id`, только
  `connection_id` + `server_country_code` (выбор новой ноды).
- **Смена IP той же ноды** — тот же `node_id`, `/v1/config` отдаёт новый host;
  периодический refresh клиента подхватывает.
- **Нода снята** — нет в `/v1/services`; `/v1/config` по старой паре → 404;
  клиент после re-sync удаляет карточку.
- **Несколько IP у одной ноды** — отдельно, см. `api-node-ips-proposal.md`
  (`node_ips` при том же `node_id`).

## Клиент (Dopamine) — уже / сделаем

Уже:

- Шлём `connection_id` и `node_id` (если есть в `apiConfig`) на install /
  refresh / reconnect.
- При импорте подписки сохраняем оба поля; дедуп карточек по паре.
- На connect при ошибке API и живом локальном конфиге — fallback без фейла
  туннеля; тосты на фоновых fetch глушим.

Сделаем после контракта:

- На `node_not_found` + есть локальный конфиг → тихо; один раз re-sync
  `/v1/services` и пересборка списка (убрать мёртвые пары).
- Не показывать «Error when retrieving configuration from API», если
  подключение всё равно возможно с кэша.

## Acceptance

- [ ] Каждый элемент `connections[]` в `/v1/services` содержит и
      `connection_uuid`, и `node_id`.
- [ ] Две ноды с одним `connection_uuid` имеют **разные** `node_id`.
- [ ] `/v1/config` с парой возвращает конфиг с host именно этой ноды
      (проверяется на 2+ нодах одного uuid).
- [ ] `/v1/config` с несуществующим `node_id` → 404 `node_not_found`, не
      конфиг соседней ноды.
- [ ] После удаления ноды из каталога её нет в `/v1/services`.
- [ ] Смена IP при том же `node_id` отражается в следующем `/v1/config`.

## Вне скоупа

- Делать `connection_uuid` уникальным per нода (альтернатива «только uuid») —
  не нужно, если пара стабильна.
- Менять формат самого wire/VLESS конфига.
- `node_ips` — отдельный proposal.
